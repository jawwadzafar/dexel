# Pixel-art authoring

Art here is **generated by committed code**, not hand-drawn binaries.
`tools/gen_assets.py` is the source of truth; `assets/*.png` (82 files as of
the v2 manifest) are build outputs that happen to be committed. Any sprite is
re-derivable, diffable, and editable by changing a few numbers — nobody is
ever blocked on a binary they can't open. Regenerate with:

```bash
python3 tools/gen_assets.py
```

This self-checks on every run (size, palette/ramp purity, opaque-pixel count,
the chair hard-region constraint, the two frame-difference rules, the
monitor's exact screen rect) and **exits non-zero** on any failure — a botched
edit cannot quietly ship a blank, off-palette, or mis-anchored asset. It also
deletes any stale file not in the current manifest.

## Hard rules

1. **No anti-aliasing, ever.** `from PIL import Image` only — **never import
   `ImageDraw`**; its `ellipse`/`arc`/`line` primitives anti-alias, which is
   the single fastest way to lose the pixel-art look. Plot pixels through the
   generator's own `Sprite` class (`s.dot()`, `s.rect()`, `s.hline()`, hand
   pixel-lists) so a colour name is the only thing you can ever write, and an
   off-palette or soft-edged pixel is impossible by construction.
2. **NEAREST only, never resize in the generator.** Author every sprite at its
   native manifest size; the only resize the generator ever does is an integer
   `Image.NEAREST` downsample (÷1/÷2/÷4) when deriving store thumbnails. The
   game/frontend does the *upscale* with nearest-neighbour (`image-rendering:
   pixelated` in CSS) — never author at 2x and shrink, never let anything
   scale by a non-integer factor.
3. **Palette purity — 18 colours, referenced by name only.** Define the
   palette once as `name -> RGB`; a hex literal anywhere else in a drawing
   call is a smell. The self-check asserts every opaque pixel of every
   palette-authored file is one of the 18 (`docs/art-direction.md` has the
   exact table); anything else fails the build.
4. **Determinism.** No unseeded RNG, no time/locale input. A re-run with no
   source change must rewrite byte-identical PNGs — screenshots are a
   verification artifact (see `feature-build-and-verify`), and non-deterministic
   art makes them useless for diffing.
5. **Contact shadows.** Anything resting on a surface ends in a 1px `shadow`
   row wider than the object itself, or it reads as floating.

## The 5-step ramp exception (recolourable parts)

N colours must not cost N sprites. A recolourable part (currently the hoodie
and the chair) ships as two same-canvas PNGs:

- **`*_form.png` — grayscale only**, from exactly this ramp (`RAMP` dict in
  `gen_assets.py`), palette-purity **exempt** and ramp-purity **checked**
  instead:

  | Step | Hex | Meaning | Composites to (of the runtime tint) |
  |---|---|---|---|
  | ramp1 | `#4d4d4d` | deep fold / underside | 30% |
  | ramp2 | `#7a7a7a` | shadow side | 48% |
  | ramp3 | `#a8a8a8` | mid tone | 66% |
  | ramp4 | `#d4d4d4` | **base fabric** | 83% |
  | ramp5 | `#ffffff` | specular edge, <5% of pixels | 100% |

- **`*_detail.png` — palette-pure**, drawn over the form: the 1px `shadow`
  silhouette outline plus any fixed-colour hardware.

Runtime tint hexes (`indigo`, `cobalt`, `neon`, ...) live in exactly **one**
place — the Go catalog's tint table — and are **never** painted into a PNG.
The frontend composites `tint * ramp_value / 255` via a CSS mask+multiply
pair (`docs/art-direction.md`, "The CSS tint mechanism").

### The tint-crush lesson — the trap that actually shipped once

**Author the large flat areas at ramp4 (83%), not ramp1/ramp2, and verify at
the game's DEFAULT tint — never at a neutral/mid-gray mockup.** The first hero
pass authored the hoodie's fold shading too dark; at the default `indigo`
tint (`#6a5aa0`), the runtime multiply crushed every fold to near-black —
invisible on a mid-gray isolated PNG preview, glaringly obvious the moment it
was rendered in the real running game. The fix: author the base fabric at
step 4 so a tint has *headroom* for a highlight, reserve steps 1-2 for small
deep-fold accents only, and — this is the actual process fix, not just the
art fix — **judge the result composited in the real game at the default tint,
then again at the darkest purchasable tint**, never in isolation. (The
darkest tint, `slate` `#2b2b33`, is nearly `wall_dark` — low fold contrast
there is a known, accepted limitation, not a bug to re-chase.)

## Ordered (Bayer) dithering — more apparent shades than you have colours

`gen_assets.py` has three helpers built on a fixed 4x4 Bayer matrix
(deterministic, not RNG — still palette/ramp-pure because each call only ever
emits one of its two named input colours, at varying density):

- **`bayer_mix(x, y, ratio, lo, hi)`** — the primitive: picks `hi` for
  approximately `ratio` of pixels in a fixed repeating pattern, `lo` for the
  rest. Use for a two-colour dithered gradient (e.g. a bezel bevel).
- **`ramp_dither(x, y, v)`** — `v` is a continuous 0.0-4.0 position on the
  5-step ramp; dithers between the two neighbouring ramp steps so a shading
  gradient reads smoother than 5 flat bands while staying ramp-pure. Use this
  for fold creases, shoulder-blade shading, ambient occlusion on any `*_form`
  sprite.
- **`radial_dither_glow(sprite, cx, cy, rx, ry, x0, y0, x1, y1, colour, gain,
  gamma)`** — paints one palette colour at a density that falls off radially,
  for glow pools / light blooms, instead of a hard-edged rect. **Clip it to a
  bounded box** (the `x0..x1, y0..y1` args) — the first attempt left it
  unbounded and bled a cloud of dither dots onto the wall above the monitor
  (the rejected "particles" artifact). Always pass a box tight to the light
  source's actual span.

**One light direction for the whole scene.** Every shading helper (`hgrad`,
the AO helpers, the glow) puts its highlight upper-left and its shadow/AO
lower-right, matching the room's one lamp. Never light a new sprite from a
different angle — it will read as physically wrong next to everything else,
even if nobody can articulate why.

## Self-check before handing off

```bash
python3 tools/gen_assets.py   # exits non-zero on any assertion failure
```

Read its own output: per-file size/opaque-count/palette-or-ramp status, the
chair hard-region assertion (no chair pixels above room row 120 inside
x 116..204 — would occlude the keyboard), the frame-difference assertions
(typing A/B differ only in forearm pixels; buddy_bot_a/b differ in exactly 2
eye pixels), the monitor screen-rect assertion, and the stale-file cleanup
list.

**Then render the real game and judge it — never the PNGs in isolation.**
Isolated/mid-gray mockups hid both real defects this project shipped (the
tint-crush above, and a "double-hump" character silhouette that read as two
bald figures once composited with occluding desk props). See the
`feature-build-and-verify` skill for the exact build+screenshot recipe; the
short version:

```bash
cd app && go build -o /tmp/dc . && \
  DEVCOMPANION_FAKE_SCRIPT="type:20s,idle:40s,mouse:15s" \
  /tmp/dc -provider fake -addr 127.0.0.1:8099 &
npx --yes playwright screenshot --viewport-size=640,400 \
  --wait-for-timeout=3000 http://127.0.0.1:8099/ /tmp/dc-shot.png
```

If you are a model with native vision (a Claude agent): **read the screenshot
directly and judge it with your own eyes** — do this at the DEFAULT tint
first, then at least one other tint if the part is tintable. `scripts/visual-check.py`
is a fallback for text-only models only; if it contradicts what you can
plainly see in the image, trust your eyes.

## Readability checklist for anything new

- Silhouette over detail: at native size (88x104 for the developer, 40x44 for
  desk slots, 28x30 for buddy), can you tell what it is without upscaling? If
  not, simplify — don't add pixels.
- Two-frame animation pairs (typing A/B, blink A/B) differ **only** in the
  pixels that actually move; run `check_frame_diff` mentally — if the diff
  bbox covers the whole sprite, it will jitter, not animate.
- Every recolourable part gets a 1px `shadow` silhouette outline in its
  `*_detail`/base layer — this is what keeps the silhouette separating from
  the background at every tint in the table, including the ones close to a
  background colour.
- New manifest entries: update `docs/art-direction.md`'s tables first (the
  doc is normative; where its prose and its layer/manifest list disagree, the
  prose wins per that doc's own rule), then `SPEC` in `gen_assets.py`, then
  run the generator.
