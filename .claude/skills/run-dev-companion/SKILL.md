# Run Dev Companion

Orchestrator for the **dexel** fleet — a cozy pixel-art desktop companion whose
workday runs on real typing. Go server + WebSocket + a committed TypeScript
bundle, shipped as one binary; the product is `app/` (ADR 0011). The frozen
Rust/Bevy game is archived on branch `attic/legacy-rust-and-fleet` (ADR 0020).

**You orchestrate; you do not implement.** Every code, art, or doc change goes
through a subagent with exclusive file ownership, and every "done" is
re-verified here from a clean build/cache before it is believed. The plan is
`docs/plan/ROADMAP.md` and the event log is `docs/plan/ORCHESTRATION-LOG.md` —
both tracked, both read before planning, the log appended as work lands. See
the `orchestration-playbook` skill for the full method.

- Pattern: **pipeline** · Execution: **subagents**
- Agents: `game-architect`, `game-engineer`, `pr-reviewer-correctness`, `visual-verifier`, `game-artist`, `pr-reviewer-boundaries`, `pr-reviewer-tests`, `pr-merge-decider`
- Workspace: the repo itself — no separate agent workspace. `docs/plan/ROADMAP.md` is the plan and `docs/plan/ORCHESTRATION-LOG.md` is the append-only event log; agents report their results back to you directly.

## Phase 0: Context check

Before anything, read `docs/plan/ROADMAP.md` and the tail of
`docs/plan/ORCHESTRATION-LOG.md`:
- The log shows phases already merged **and** the user asks for a partial fix → **partial re-run**: invoke only the affected agent(s), briefing them with the relevant log entries.
- The log shows a run in progress (a phase opened but not merged) → **resume** at that phase rather than restarting it.
- Nothing relevant in the log → **initial run**: plan from the roadmap.

## Invocation

Invoke each agent with the Agent tool using its definition in `.claude/agents/` (subagent_type matches the agent name). Launch parallel groups in one message with `run_in_background`; collect results before gated phases.

## Phases

### Phase 1: Architecture
**Execution mode:** subagents

Agents: `game-architect`.
- `game-architect`: A plan precise enough that an engineer can implement it phase by phase without re-deriving architecture decisions or guessing scope.
. Hands off to `game-engineer` (artifact: `docs/plan/ROADMAP.md`, plus a `docs/plan/<PHASE>-design.md` when the phase needs one).

**Gate before next phase:** docs/plan/ROADMAP.md names the phase and every phase in it has a command-verifiable exit criterion (go vet/build, bash scripts/test-race.sh, npm run typecheck && npm run build with no bundle drift)

### Phase 2: Phase cycle (one shippable slice at a time)
**Execution mode:** subagents

Agents: `game-artist`, `game-engineer`, `pr-reviewer-correctness`, `pr-reviewer-boundaries`, `pr-reviewer-tests`, `visual-verifier`, `pr-merge-decider`.
- `game-artist`: A cohesive cozy pixel-art look matching docs/art-direction.md, where a vision model shown a screenshot describes it as finished pixel art — never as placeholder rectangles.
. Hands off to `game-engineer` (artifact: `app/assets/`, generated by tools/gen_assets.py).
- `game-engineer`: Each phase builds, passes go vet + scripts/test-race.sh + the frontend typecheck/build with no bundle drift, is seen working in the real running app, and lands as its own reviewable PR before the next phase starts.
. Hands off to `pr-reviewer-correctness`, `pr-reviewer-boundaries`, `pr-reviewer-tests`, `visual-verifier` (artifact: `docs/plan/ORCHESTRATION-LOG.md`).
- `pr-reviewer-correctness`: A verdict on plan/exit-criterion adherence backed by commands this agent ran itself, in its own worktree.. Hands off to `pr-merge-decider` (artifact: its verdict, returned to you and routed into `pr-merge-decider`'s brief).
- `pr-reviewer-boundaries`: A verdict on the activity-isolation boundary, no-raw-content-persistence, the anti-mashing clamp, and go vet / tsc --strict cleanliness.. Hands off to `pr-merge-decider` (artifact: its verdict, returned to you and routed into `pr-merge-decider`'s brief).
- `pr-reviewer-tests`: A verdict on test adequacy and a from-scratch raced test run (bash scripts/test-race.sh, after go clean -cache -testcache), independent of whatever the engineer already ran.. Hands off to `pr-merge-decider` (artifact: its verdict, returned to you and routed into `pr-merge-decider`'s brief).
- `visual-verifier`: A verdict on whether the phase's stated visual behaviour is really visible in the real running app, quoting the description it judged as the evidence.
. Hands off to `pr-merge-decider` (artifact: its verdict, returned to you and routed into `pr-merge-decider`'s brief).
- `pr-merge-decider`: Every phase PR ends either merged into main with a logged commit SHA, or explicitly left open with every reviewer's required fix stated in one place.
. Terminal agent — its output is (part of) the final deliverable.

**Loop — iterate until done (max 30 passes):**

Stop on whichever of these three comes first:
1. **Success** — the exit condition holds: _every phase this run was asked to deliver has a merged PR recorded in docs/plan/ORCHESTRATION-LOG.md, in order. Within each phase's sub-cycle: game-engineer opens the PR first; the three reviewers run concurrently with each other but only after that PR exists, each in its own git worktree; pr-merge-decider runs only after all three reviewer verdicts are in, and merges or requests changes. game-engineer does not branch for the next phase until pr-merge-decider has merged the current one._ Require evidence for the call, not an assertion that it looks done.
2. **No progress** — 3 consecutive passes produce no material change. A pass that fixes nothing will not start fixing things on the next attempt; stop and report the sticking point.
3. **Cap** — 30 passes are spent. Proceed with the shortfall recorded in `docs/plan/ORCHESTRATION-LOG.md` and the final report; a bounded, documented gap beats an unbounded loop.

Between passes, re-run this phase's agent(s) with the **specific failures from the last pass appended** to their brief — refine, do not restart from scratch.

**Gate before next phase:** docs/plan/ORCHESTRATION-LOG.md has a Merged decision with a commit SHA for every phase this run owned, or the run stopped early with a documented blocker recorded there. Re-verify each merge yourself from a clean cache — an agent reporting green off a stale cache has already happened in this repo.

## Data flow

- Agents report their results **to you**, in their reply. There are no coordination files: you are the router, so a result you do not carry into the next brief is lost. Verify an agent's stated artifact actually changed on disk before treating its phase as done — a claim is not evidence.
- **Pass work by citing paths, not by restating file contents.** Give the next agent the artifact path (`docs/plan/ROADMAP.md` §F3, `app/internal/engine/`) and what to do with it. Every paraphrase between producer and consumer loses detail the producer thought was obvious, and those losses compound down the chain.
- Durable state lives in the repo: `docs/plan/ROADMAP.md` (the plan) and `docs/plan/ORCHESTRATION-LOG.md` (append-only, one dated row per launch/landing/verdict). Append as work lands, not at the end — a run interrupted mid-phase must be resumable from the log alone.
- Each pass, restate what is still outstanding rather than only appending to it; keeping the open items in view keeps the objective in view as the run gets long.

**Precedence.** Where this playbook conflicts with a skill, the skill wins for methodology and this playbook wins for sequencing and scope. Where it conflicts with the user's explicit instruction, the user wins — say what you are overriding and why.

## Error handling

- Agent fails → retry once with the failure appended to its brief. Second failure → proceed without that output and record the gap in `docs/plan/ORCHESTRATION-LOG.md` and the final report.
- Conflicting outputs from parallel agents → do not discard either; present both with sources and either resolve via a named criterion or escalate to the user.
- A report missing its acceptance criteria → send it back to the producing agent once; then accept with a `PARTIAL` marker.

## Completion

1. Confirm every phase this run owned is recorded in `docs/plan/ORCHESTRATION-LOG.md` as merged, or dropped with a reason.
2. Summarize deliverables + gaps for the user.
3. Ask one short feedback question ("anything to improve in the result or the workflow?") — if feedback arrives, route it: output quality → the agent's skill; role gaps → agent definition; ordering → this orchestrator; then append a row to `docs/HARNESS-CHANGELOG.md` recording what changed, where, and why.

## Test scenarios

- **Happy path:** run the full pipeline across all agents on a small representative input; every phase ends with a merged PR recorded in `docs/plan/ORCHESTRATION-LOG.md`.
- **Failure path:** kill one mid-pipeline agent (simulate by making its input unavailable); the run must complete with a documented gap, not stall.
